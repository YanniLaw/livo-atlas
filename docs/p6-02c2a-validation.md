## 证据复核入口

`run_acceptance.py` 顺序执行 SDK、Noetic、Humble 各模式，完成的结果使用 `final` 命名。
`compare_replays.py` 生成每次回放的 `strict-checks.json`，核对同平台 C1 数组、发布、参数和资产。
`run_proposer.py` 的证据在 `retail-{noetic,humble}-final.run-evidence.json`，
包含原文件 SHA256、实际进程及加载库、CPU/OMP/nice、RSS、耗时、全部 YAML 内容和版本链。
具体查询和完整更新分别保存在输出目录的 `queries/` 与 `proposals/`。

`check_final_evidence.py` 已通过，结果记录于 `final-evidence-check.log`，并生成 `final-evidence.json`；它汇总 XML 根用例数、安装消费者、8 次回放、
两次离线工具、源码副本及官方 bag 摘要。
`--verify-existing` 只重核已有证据，要求与保存的报告一致。
冻结的 Noetic/Humble 源码逐文件比对归档；当前仓库仅允许文档不同于冻结产品提交。
Noetic devel 回放文件已被后续静态构建替换，其运行时摘要按完整/短段记录配对核对；
保留的 Noetic 提案工具与 Humble 安装文件还会重新计算摘要。
脚本和本机路径属于包外证据，跨电脑需按实际依赖位置调整。

最终核对确认两端冻结源码的 399 个普通文件逐字节一致，归档及原始 bag 摘要不变；
Humble 的 37 个保留安装文件和 Noetic 提案工具实际产物重新计算摘要一致。
最终产品代码冻结后仅更新文档，没有为增加提案数量调整默认阈值。
