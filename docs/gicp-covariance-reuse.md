# GICP 协方差计时与复用

本轮核对本机 PCL 1.10 与 Humble 的 PCL 1.12 实现。协方差计算使用未变换的点云、
相同邻域数和 GICP epsilon。两个方向保留相同点序，迭代只读取协方差。
不修改公开 API、匹配参数、质量阈值或归档格式。

## 实现与指标

现有私有 Gicp 子类在计时开启时初始化源搜索树，依照 PCL 的目标在前、源在后顺序，
调用 PCL 自身的 computeCovariances，再交给基类执行迭代。基类检查到数组已存在，
源树也已初始化，不重复构建。关闭计时则直接委托基类处理未缓存的协方差和迭代，
所有新增计时点不读取时钟。

| 指标 | 范围 |
| --- | --- |
| loop_gicp_source_tree | 源搜索树初始化；目标树仍在 align 的初始化中 |
| loop_gicp_covariance_target / source | 实际执行的各自协方差计算 |
| loop_gicp_iterations | 基类 computeTransformation，包括初始化、对应搜索、估计器、检查和收敛处理 |
| loop_gicp_estimate | 刚体估计器调用耗时，包括正常返回和抛出异常 |
| loop_gicp_transform_check | 原有逐次变换安全检查 |

指标互相包含。最初版本只记录正常返回的估计器；后续补齐了异常调用耗时，原异常继续
交给 PCL 处理。下列历史对照中的估计器小计仍不完整，不能推断全部估计器成本。

后续 CPU 采样还发现，历史回放加载的线程审计探针对每次 FLANN 查询中的 OpenMP 调用
执行 `dladdr`，显著影响耗时。下列时间只代表带探针运行；计算次数、数值和归档对照
仍有效。日常性能应使用 [去除线程探针的采样与重复对照](gicp-cpu-profile.md)。

正向结束后保留两组数组，反向交换源/目标角色，在 setInputSource/Target 之后通过
PCL 的协方差 setter 设置。仍使用两个独立求解器，不复用变换、收敛状态或搜索树。
输入点云不原位改写，数组不跨候选共享。正向失败或达到迭代上限时保持原有退出路径。
反向结束后立即释放数组，再进行全分辨率质量检查。

代价是在两个方向之间保留数组。每个点一个 3×3 double 矩阵，公共下采样上限为
每块20000点，两组约2.88 MB；不是额外复制两组数据。相同点序、邻域参数、epsilon
和默认搜索表示是复用前提，未来改变这些条件时需要重新核对。

## 验证

SDK 76 个 CTest 目标、Noetic 3 个相关目标、Humble 5 个相关目标通过。
缺失细分计时的开关测试先失败后通过；正反协方差仅计算一次的测试先发现重复样本，
复用后通过。测试比较了开启/关闭计时的位姿、迭代次数与同步入口结果，补充了可选结果
和候选数的前置断言，保留原有迭代上限、非法几何、退化和输入不可改写用例。
独立源码复核无重要问题。

前端预算2、后台线程4、驻留预算3，在同一 CPU 集合完整回放 Retail_Street。
有细分计时但无复用的基线也通过上一版的完整资产与数学诊断对照。

| 项目 | 无复用 | 复用后 |
| --- | --- | --- |
| 正向/反向配准次数 | 20 / 18 | 20 / 18 |
| 源协方差数组计算次数 | 38 | 20 |
| 目标协方差数组计算次数 | 38 | 20 |
| 协方差计算累计时间 | 5.136 s | 2.685 s |
| 迭代整体累计时间 | 7.020 s | 7.541 s |
| 双向 GICP 累计时间 | 12.178 s | 10.247 s |
| 验证批次累计墙钟时间 | 12.367 s | 10.988 s |
| 查询计算累计墙钟时间 | 16.021 s | 14.234 s |

数组计算由76次降至40次，减少约47.4%。各子阶段并非独立，不能直接相加。
时间只是一次配对观察，迭代时间本身也有波动，不承诺固定加速比。

两组均完成1352次LIO、1351次VIO、172个关键帧、13次查询、20个候选及2次接纳，
最终位姿版本为2。原始资产、轨迹、成员修订与语义输出字节一致；去除时间后的全部数学
诊断、迭代次数一致，最终位姿与旧基线误差小于1e-12，归档检查为consistent。
上轮质量计算的反向查询次数仍为273912，没有改变对应关系。

证据位于 validation/gicp-covariance-20261125。短 bag 结果不能替代长序列验证。
后续已补齐失败估计器子计时，并进行了 CPU 采样与不加载线程探针的对照，见
[采样记录](gicp-cpu-profile.md)。是否继续复用搜索结构，应依据新的测量结果决定。
