# 首帧激光前的传感器暂存设计

2026-11-15。基于 `fefba40`；本设计是 C3b-02 之后的独立行为修正。用户已授权当前会话自主
实施与验证。选择和默认值由执行者按这一授权确定。

## 问题与证据

`LivoSystem::AddImu` 和 `AddImage` 在接收到首个有效激光扫描之前直接拒绝数据。ROS 的三个
订阅各自排队，回调到达次序不一定与各传感器采集时间一致；IMU 初始化使用的样本因而可能随
启动时序变化。上阶段保留的异常可由两条初始化 IMU 未进入前端精确复现，但原始异常没有逐条
接收记录，不能断言其当时的准确回调顺序。

本次另以 Retail_Street 的前 3.2 秒构造两份短 bag：三个话题的消息内容、每话题顺序和数量
逐字节一致，仅调整首帧激光的播放时间，并将首帧图像放到两种情况的激光之后。旧代码在两种
情况分别从 `946685437.510941982` 和 `946685437.620972037` 的 IMU 开始初始化，LIO/VIO
更新数分别为 29/29 和 28/28。实验及哈希位于工作区
`validation/startup-sync-20261115/`；构造数据用于控制到达次序，不代表新的真实数据集。

## 方案选择

1. 仅修改 bag 播放顺序：保留原行为，但不能解决真实设备或 ROS 回调先后问题。
2. **在普通 C++ 核心暂存首帧前传感器数据**：只调整启动期，两个 ROS 与独立 SDK 共用；需要
   明确容量、溢出及旧行为的兼容方式。
3. 为整个运行期引入跨话题时间重排和水位线：能处理更多延迟，但增加持续延迟、内存及缺包策略，
   超出当前问题。

采用方案 2。默认启用；`common.buffer_before_first_lidar: false` 可恢复过去的丢弃行为。
这会改变首帧前确有 IMU/图像到达时的初始化输入和后续数值，是明确的行为修正；常规首帧之后的
滤波、传感器同步、地图、时间校正和 ROS 接口不变。不宣称新结果的绝对精度一定更高。

## 规则与边界

- 暂存只在首个**时间非负、成功预处理且非空**的激光扫描到达前发生。无效/空扫描不能清空或
  释放暂存。核心原有逻辑用负值表示尚无激光时间，本次保留该约定，不扩展负传感器时间支持。
  首帧到达后先建立激光时间锚点，按原到达顺序将暂存 IMU 接入现有队列，再允许处理同步结果。
- 首帧前最多保留 2,000 条 IMU、8 张已通过既有采样和时间检查的图像；满时丢弃最旧项，保留
  最近的数据，并记录溢出计数。上限是消息数，不是对单张图像或整进程的字节上界。
- 启用暂存时，`AddImu`/`AddImage` 返回 `true` 表示已接收暂存，不保证之后一定参与估计；
  后续溢出、过期图像、IMU 时间回退或时间范围错误仍可能使其不参与。关闭选项时保留旧返回值
  和首帧前拒绝行为。
- IMU 在进入暂存时执行已有有限值和偏移/时间范围检查；首帧到达后再基于该激光时间执行既有
  `ros_driver_bug_fix` 校正和单调性检查。校正后非法的暂存项单独丢弃并计数，不让首帧激光
  回调抛出该项的时间异常。正常首帧之后仍沿用既有规则。
- 图像在到达时执行既有 Hilti 每四帧采样、去重和时间回退检查；进入现有图像队列，过期图像
  仍由同步器按采集时间丢弃。首帧之前的采样计数与正常到达顺序一致。
- 首帧迟迟不来时缓存保持有界；关闭输入且仍无首帧时释放暂存。为普通 SDK 提供只读统计，
  两端节点在已有输入计数处汇报缓冲溢出和暂存 IMU 校正拒绝数。
- 在各话题自身保持有序、消息未丢失、初始队列未溢出且首帧之前的数据均在首次同步处理前
  到达的条件下，首帧与 IMU/图像回调相对顺序不应改变结果。有限缓存、消息丢失、同话题乱序、
  首帧后迟到的旧消息、激光时钟回退及 `ros_driver_bug_fix` 在后续扫描上的锚点变化不在此保证内。
- 不更改 vikit；Google C++17、直接成员、函数实现间空行；继续使用同一 ROS1/ROS2 main。

## 验收

1. 普通 C++ 测试覆盖两种首帧相对顺序输出一致、关闭开关时旧拒绝行为、空扫描、非有限数据、
   IMU 偏移及 driver fix、回退、Hilti 采样、溢出和无激光关闭输入。
2. 真实 Noetic 对上面两份短 bag 重跑：每话题输入哈希和数量相同、两种启动顺序下四数组及
   旧发布语义一致；显式关闭选项时仍能复现旧顺序差异。
3. Humble 用同样的受控场景验证共享入口和参数；两端均用原始 Retail_Street 完整回放验证
   正常处理、关闭选项下与同平台旧基线一致。启用选项的不同数值如实记录，不宣称与旧基线相同。
4. 记录命令、结果、峰值及跨机器依赖；独立审阅后保留 `framework_completion` 本地分支。
