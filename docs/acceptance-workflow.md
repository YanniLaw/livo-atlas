### 状态转换

```text
待细化 → 可实施 → 实现中 → 待用户验收 → 用户验收通过
                             ↓
                           需返工 → 实现中
```

缺少数据、环境或依赖时可以标为“受阻”，写明恢复条件。未测、部分通过、无法复现都不能标成通过。用户只回复“继续”而未明确当前任务验收结论时，不自动推断测试已通过，应确认其含义。

“实现完成”只是进入待验收的条件。任务表和验收记录保持同一状态。文档生成成功不改变任何实现任务状态。

## 3. 任务粒度

一个任务围绕一个可观察结果，具有独立修改边界、独立测试步骤和失败定位方式。涉及多个文件是允许的，但不要把目录移动、数学修改和外部行为变化放进同一项。

如果一项需要多个不同数据集才能解释不同功能，或失败时无法确认是哪种修改导致，应拆为 `P1-xx.a`、`P1-xx.b` 等子任务。父任务只有所有必要子任务验收通过才通过。

阶段文档中的任务卡是草案。开工前将卡片补全为具体执行单，不把待定命令包装成可直接运行的步骤。仅需用户提供的环境或数据阻塞当前项时再提出具体问题。

## 4. 开工前的执行单

每项至少填写：

1. ID、目标、前置任务及其验收记录。
2. 要修改的实际文件、允许变化与兼容要求。
3. 输入数据路径/标识、配置、运行模式和时间范围。
4. 本地编译、启动、回放、检查与退出命令；标明工作目录。
5. 可观察输出及通过门限，包含必要的异常场景。
6. 影响范围和恢复方法；使用独立输出目录，避免覆盖已验收结果。

目标硬件或数据未确定时，性能门限标为待定，该任务不得以主观“够快”通过。浮点算法对比使用已确认容差，不强求没有依据的逐位一致。

## 5. 每次交付

助手提供变更摘要、文件清单、已做自检及限制、用户可执行步骤、预期结果和结果保存位置。区分“预期”和“实际观察”，没有运行的命令不能记成已执行。

用户完成本地测试后反馈：通过/不通过/部分通过、实际现象及必要日志。助手将明确的结论写入对应记录，保存版本/补丁标识、配置和数据引用。

失败时继续处理同一任务，保留失败记录和修订历史，不提前进入依赖任务。部分通过时列出剩余项目，直到全部满足或用户明确调整范围。

## 6. 回归与版本追踪

- 代码版本使用 commit 标识；未提交时记录基准 commit 和本任务 diff/文件清单，不擅自创建提交。
- 配置、数据时间段、目标环境与结果路径同时记录。
- 用户验收通过后修改了该任务的关键逻辑，必须登记受影响项并重新验收。
- 恢复只针对本任务改动，不覆盖用户已有改动；实际恢复前核对工作区。
- 阶段关闭条件：必要任务全部通过、无阻断问题、阶段整体回归获用户确认。
- 验收例外或范围调整由用户明确确认并记录；被排除的功能标明未验收，不写成已通过。
