# GICP CPU 采样与异常计时

本轮保持原有匹配、质量阈值、迭代限额和公开接口，仅补齐失败估计器的耗时。
采样工具只解包到工作区验证目录；没有安装系统软件或调整内核权限。

## 计时修复

`loop_gicp_estimate` 现在包含正常返回和抛异常的调用。PCL 会在迭代循环内部捕获估计器的
异常，因此仅在 `estimate()` 返回后记录会漏掉失败调用。包装函数现在先记录耗时，再用
`throw;` 保留原异常；变换安全检查仍只在估计成功后执行。关闭计时时仍使用空时间点，
新增路径不读时钟或打印阶段日志。各父子阶段互相包含，不能重复相加。

回归测试使用相距100米的两块真实测试几何，使对应点数为零，实际触发 PCL 的
`NotEnoughPointsException`，不注入替代估计器。修复前测试因缺少样本而失败；修复后
确认失败调用只记录一次，且计时开关不改变收敛状态、迭代数或拒绝结果。

## 采样方法与探针干扰

本机没有 perf，`perf_event_paranoid=4`。采用 Ubuntu gperftools 2.7 的 `libprofiler`，
以默认进程 CPU 时间源、100 Hz 采样。只给冻结的 mapping 程序加载该库，不给 roscore、
回放进程或验证工具加载。使用 `google-pprof --text` 解析，再用
`--focus='GeneralizedIterativeClosestPoint.*computeTransformation'` 筛选迭代调用栈。
这是 CPU 栈样本，不是各线程的墙钟时间；系统库缺少完整符号的条目不能当作精确源码行。
两次 CPU 采样都使用 `af8674d` 的修复前求解器，其213个估计器样本仍仅覆盖正常返回。
采样用于定位原有计算与探针开销；异常计时修复另由真实失败用例和修复后的非采样回放验证。

首轮保留了先前用于确认实际团队数的 OpenMP 审计探针。采样发现，探针对每次
`GOMP_parallel` 都调用 `dladdr` 判断所属库，而 FLANN 的每个查询也经过该入口。
控制回放记录约155万次其他库的单线程并行区，造成明显额外开销。
首轮迭代调用栈的534个样本中，399个落在 `_dl_addr`，不是算法计算本身。

因此历史带探针数据只能用于审计配置、比较计算次数与数值一致性，不能直接代表部署性能。
本轮保留控制数据，重新进行不加载该线程探针的采样和非采样对照。候选审计只在20次
验证调用的边界采集时间，所有对照使用同一实现。完整回放固定前端2线程、后台4线程、
几何驻留预算3和 CPU 集合 `2,4,6,8,10,12`；其他参数相同。

不加载线程探针的采样回放中，GICP 迭代累计0.455秒，双向配准累计0.665秒，
候选验证批次累计墙钟0.872秒，查询计算累计墙钟2.513秒。带线程探针的采样控制中，
迭代为8.906秒，查询计算为16.013秒。两者都加载了 CPU profiler；这是探针干扰的观察，
不作为产品版本的加速比。

无线程探针的迭代调用栈仅46个 CPU 样本：16个直接落在 FLANN `searchLevel`，
8个经过 BFGS `minimizeOneStep`。样本较少，且系统运行库有不完整符号，足以提示
近邻搜索仍值得留意，不足以精确划分搜索、Mahalanobis 矩阵与运行库的百分比。
没有发现必须改变 PCL 迭代路径的证据，本轮不继续复制算法或引入新的搜索缓存。

## 回归与配对范围

SDK 全部76个 CTest 目标、Noetic 的3个相关目标和 Humble 的5个相关目标通过。
Humble 只做构建和相关测试，完整 bag 均在原生 Noetic 上运行；容器已恢复停止。
独立源码复核没有发现重要问题。可后续增强的测试是直接断言失败状态
`LoopStatus::kNotConverged`；当前用例将状态与公共关闭计时入口比较，重点覆盖计时
开关的结果等价和失败调用恰好记录一次。

非采样配对比较 `af8674d` 与本轮异常计时修复，均已包含协方差复用，不衡量该复用的
加速比。正常估计后的安全检查仍为213次；修复版额外记录两次失败估计，计时共215次。
时间为阶段累计值，双向配准包含迭代，查询还包含准备、验证、接纳与排队，不能相加。

| 累计时间，秒 | 第1组修复前 | 第1组修复后 | 第2组修复前 | 第2组修复后 |
| --- | --- | --- | --- | --- |
| GICP 迭代 | 0.354 | 0.333 | 0.338 | 0.352 |
| 双向 GICP | 0.534 | 0.530 | 0.517 | 0.537 |
| 验证批次墙钟 | 0.869 | 0.785 | 0.782 | 0.897 |
| 查询计算墙钟 | 2.783 | 2.568 | 2.899 | 3.194 |

两组配对的耗时变化方向相反，不能归因于本轮修复或宣称稳定加速。四次运行均完成
1352次LIO、1351次VIO、172个关键帧、13次查询、20个候选和2次接纳，最终位姿版本2。
原始帧、轨迹、成员修订与语义输出字节一致；去时间字段的全部数学诊断一致，最终位姿
相对旧基线的最大矩阵元素差为0，所有归档检查均为 `consistent`。

本轮收敛在测量修复和验证记录，不扩展算法。后续若继续性能优化，应先测无线程探针时
的几何准备及结果交付尾延迟；目前没有优先更换搜索结构或放宽配准阈值的依据。

## 复现与证据

证据目录为工作区的 `validation/gicp-cpu-20261125`。保留 profiler 包、采样文件、
解析结果、运行脚本、冻结源码与库、归档检查和逐资产比较。每次回放使用新输出目录。
新的不可变原始帧资产校验 SHA256 后硬链接到已有参考资产，降低磁盘占用，日志和诊断保留。

另一台电脑可直接运行现有 `tools/run_baseline.py`，固定同一份 YAML 与 CPU 预算，
在独立的采样回放中给 mapping 程序设置 `CPUPROFILE` 并加载 `libprofiler`。
性能对照分别运行改动前后的程序，不加载 CPU profiler 和 OpenMP 团队审计探针。
至少重复两组，并对比轨迹、原始资产、候选顺序、去时间字段的诊断、接纳结果和位姿版本。
约135秒的 Retail_Street 只能用于本机回归，不能替代长序列真实数据验证。
