# 几何准备与优化位姿交付

本轮按已批准的方向先分析已有四次无探针完整回放，再补齐缓存诊断和优化位姿交付边界。
沿用当前 C++17 库、Task/ThreadPool/WorkQueue 和 YAML 开关，不改变 SLAM 数值行为。

## 范围与取舍

几何准备占已有查询计算累计时间的约50%～58%，完成队列等待最长不到0.3毫秒。
因此先记录每次读取的缓存命中、重建、版本切换及读取量；在现有回执处测量交付完成。
该方案只补诊断，驻留预算和所有权不变，能用少量代码验证真正的重复工作。

跨查询共享缓存可能减少重建，但需要处理任务读视图、版本、成员修订及生命周期，
目前没有足够的逐块证据支持这项复杂度，暂不实施。完整构建逐帧复制体素累计状态也是
潜在成本；旧采样中85个 AddKeyframe 样本有25个经过哈希表复制，后续需单独基准验证，
本轮保留其异常安全保证，不直接改为原位累计。

## 缓存语义

MakeGeometryReader 的可变缓存由一条查询任务图独占。查询之间不共享；同一读取器
遇到新的位姿版本会重新创建 mapper。GeometryMapper 自身可在刚体修正后保留局部数据，
局部相对位姿变化才使对应块失效。源块在每次装入目标前刷新 LRU，避免批间被驱逐。
这些是当前行为的说明，不据此认定每次重建都不必要。

开启 diagnostics.stage_timing 时，成功读取输出 loop_geometry_cache，携带块ID、位姿
版本、reader_reset、built、cloud_reads、evictions 和 resident_submaps。
计数来自 GetSubmap 前后统计差；reader_reset 表示新建读取器中的首次使用或版本切换。
不输出失败读取的成功记录，关闭开关不新增统计读取或日志。

## 位姿交付边界

现有 loop_optimization_result_latency 止于 Classify 入口，尚未验证和决定接纳；
archive_publication_wait 则混合
普通关键帧、封口和优化位姿。本轮增加两个只针对已接纳回环的阶段：

| 指标 | 起止 |
| --- | --- |
| loop_pose_delivery_latency | 查询派发到 LivoSystem 应用位姿、更新内部几何及完成订阅回调后的回执 |
| loop_pose_publication_wait | 优化位姿发布到同一次 owner 回执 |

派发时间在提交线程池之前、最终派发检查的 mutex 内采样。Publish 保存该时间，
AcknowledgeCommit 在 mutex 下消费时间戳并采样，
再恢复队列，解锁后打印。普通提交使用空时间点；关闭开关不增加时钟读取。
回调失败后不回执，因此不输出成功交付。指标不代表 ROS 订阅者或 GPU worker 已处理完结果。
父子阶段互相包含，不应相加。

## 验证方式

先用真实几何和 LivoSystem 测试诊断开关、成功回执、拒绝和回调失败，再跑 SDK 全套与
双 ROS 相关测试。仅原生 Noetic 使用 Retail_Street 做完整回放，核对资产、轨迹、候选顺序、
数学诊断、位姿版本和归档。四次历史回放直接复用，新增完整回放只用于验证新增诊断。
证据目录 validation/geometry-delivery-20261126，分析脚本与原始日志引用一起保存。

## 最终回放结果

最终程序使用 full-corrected 目录。每次分析新的运行都强制要求缓存记录和两个交付指标，
缺失不能当作零耗时通过；历史四组作为明确的旧协议输入，允许没有新指标。
两个回环各自验证发布等待不大于完整交付延迟，不只比较总和。

| 缓存观测 | 最终结果 |
| --- | --- |
| 成功请求 / 完整构建 / 命中 | 51 / 31 / 20 |
| 云读取 / 缓存驱逐 | 428 / 12 |
| 读取器重建 | 新查询5次、同查询内版本切换2次 |
| 最大驻留数 | 3 |
| 同一查询、同一位姿版本内重复构建同一块 | 0 |

20次命中均对应每个候选前刷新的源块。相同版本与块ID在不同查询中存在重复构建，
但查询拥有不同的提交视图，且预算3下已有12次驱逐，不能直接把重复键数量当作可消除的
重建次数。本轮不引入跨查询共享、扩大容量或改变失效策略。

几何准备累计1.361秒，占查询计算2.610秒的52.15%；全部构建累计1.569秒，
其中云读取0.331秒、快照0.175秒，其余1.063秒。下一处性能基准可关注新建子地图时
的体素累计与事务复制，保留逐点顺序及异常安全；本轮不宣称算法加速。

| 第1次 | 673.632 ms | 0.205 ms |
| 第2次 | 793.195 ms | 0.081 ms |

两个样本的主要开销发生在发布之前；不足以推断长时间的交付尾延迟分布。
前端 LIO P95/P99 为46.77/51.40毫秒，VIO 为18.61/20.09毫秒，与四次历史观测接近；
LIO P95 略低于历史最小值46.81毫秒，其余三个分位数位于历史范围。
VIO 有一次最大56.72毫秒，超过历史最大值范围，发生在第1185次 VIO 更新；未据单次
回放将其归因于新增诊断，也不将分位数接近解释为已经证明没有性能影响。

SDK 76个 CTest 目标、Noetic 4个相关目标、Humble 6个相关目标通过。真实回调测试覆盖
开关、回执前后、只记录一次、普通封口、外部位姿、拒绝和回调失败；Humble 容器已停止。
完整回放为1352次LIO、1351次VIO、172帧、13次查询、20个候选、2次接纳、位姿版本2。
原始帧、轨迹、成员修订与语义输出字节一致，全部去时间字段的数学诊断一致，最终位姿
相对旧基线最大矩阵元素差为0，归档检查为 consistent。

独立复核发现原派发时间在 Schedule 返回后采样，可能漏掉提交期间的工作。
用仅在测试进程加载的探针，在真实入池后注入250毫秒提交延迟，旧指标只记录21.78毫秒，
修复后记录270.83毫秒。现有条件时钟读取已移至入池前的最终派发检查锁内，无新增时钟。
该修复后重新执行全套和双 ROS 相关测试，并完成上述最终回放；初轮 full 目录仅保留为对照。
复核的重要问题已解决。
