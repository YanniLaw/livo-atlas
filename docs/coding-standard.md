# C++ 编码与设计约定

## 依据与适用范围

用户要求：严格遵循 [Google C++ Style Guide](https://google.github.io/styleguide/cppguide.html)，保持框架清晰、代码可读，避免过度开发。

新代码和本次重构覆盖的代码按该规范编写。历史代码按任务逐步迁移，不为统一外观扩大修改范围；第三方、生成代码和外部接口名称不擅自改写。格式化不能替代命名、所有权、错误处理和接口语义审查。

当前工程使用 C++17，目标环境为 Ubuntu 20.04 / ROS Noetic。官方指南当前语言版本为 C++20；本项目明确暂保留 C++17 作为兼容边界，不因采用编码风格自动升级工具链。历史 `.cpp` 文件保持现名；新文件遵循 Google 文件命名约定。任何其他必要偏离须在任务中写明位置、理由和影响，不宣称旧工程已经全面合规。

## 编码要求

- 类型使用 `UpperCamelCase`；普通函数遵循 Google 函数命名规则，访问器可采用对应字段命名。变量使用 `snake_case`，类成员带尾部下划线，常量使用 `kUpperCamelCase`。
- 使用 `livo_atlas` 命名空间；头文件自包含，使用基于项目路径的 include guard；直接包含实际依赖，不依赖偶然的间接包含。
- 格式工具以 `BasedOnStyle: Google` 为基础，工具版本在实际引入时固定，仅格式化本任务涉及范围。格式调整与行为修改分开评审。
- 类维护清晰不变量，避免公共可变状态。纯数据结构可以使用 struct；不为每个字段机械增加访问器。
- 优先值语义和 RAII。独占所有权用 `unique_ptr`；共享生命周期有明确需要时才用 `shared_ptr`；借用引用注明有效期。
- 遵循指南对异常、RTTI、隐式转换、宏和其他语言特性的限制。新代码不引入异常驱动流程或常规 RTTI 分派；已有依赖和旧实现的兼容处理需单独评估，不全局关闭依赖所需的编译能力。
- 错误处理采用当前接口足够表达的返回状态和诊断；不为少量失败情况自建通用错误框架。
- 注释解释算法依据、单位、时间、坐标、所有权与非显然约束，不重复代码表面动作。保留必要的上游出处和许可证信息。
- 实时路径避免无依据的复制、动态分配和阻塞 IO；优化以测量和当前约束为依据。

## 设计复杂度约束

每个新增模块、接口或机制，都应回答：当前哪个任务需要它？它减少了哪种耦合或重复？是否有更直接的实现？

- 没有当前使用者，不创建预留模块、空实现和未来功能开关。
- 具体类或普通函数已经足够时，直接使用；确有替换需求或稳定边界时再建立接口。
- 不默认引入插件系统、通用事件总线、依赖注入框架、模板化传感器框架或多级继承。
- 不为每个类建立线程或队列；新增并发必须说明吞吐、时延或隔离需求。
- 优先复用现有依赖，新增库需说明收益、兼容性和维护成本。
- 参数仅暴露用户有必要调节的策略，内部实现细节保持内部。
- 架构图是职责约定，不要求每个框都对应一个类、线程或动态库。
- 任务草案可以根据实测简化、合并或取消，记录原因并遵循用户验收规则，避免为了完成清单创造不必要工作。

## 每次审阅

1. 当前任务是否有多余代码、抽象、依赖或配置？
2. 命名与格式是否符合规范？兼容偏离是否明确？
3. 数据流、状态归属和生命周期能否直接看懂？
4. 时间、坐标、单位、错误与并发行为是否明确？
5. 实测证据是否支持行为和性能声明？
6. 用户本地验收步骤是否清晰，任务是否仍等待用户结论？

编码委派时将本规范与任务卡一起提供给 Luna max。主代理依据相同标准审阅，再交付用户验收。
